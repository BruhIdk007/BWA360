# M45 — Multiplayer & Challenge Modes

**Status: FUTURE / POST-MAINLINE**

## Objective

Turn the mature LexEngine/LexMod ecosystem into a reusable local and networked game-mode platform supporting cooperative, competitive, party and solo challenge modes without forking the core simulation.

M45 is deliberately late in the roadmap. It depends on the deterministic simulation, snapshot/replay work, mature platform/input/render layers and LexMod extension model already proven by earlier milestones.

## Core rule

Multiplayer is a game-mode/session layer, not a second copy of the game.

```text
                    GameModeDirector
                          |
          +---------------+---------------+
          |               |               |
       Solo            Co-op           Versus
          |               |               |
          +---------------+---------------+
                          |
                  deterministic simulation
                          |
             +------------+-------------+
             |                          |
          Local                     Network
      shared machine             session transport
```

The same rule modules should be usable locally, over System Link/LAN and through future supported network transports, including an optional Xbox Live/Xbox Network research adapter where the validated environment permits it.

## 1. Local multiplayer

### Versus — Word Duel

Two or more players compete using separate boards and independent input streams.

Possible rules:

- score race;
- HP duel;
- timed rounds;
- best-of-N matches;
- attack/status effects generated by strong words;
- optional board interference such as temporary frozen/blocked tiles;
- configurable handicaps chosen openly in the lobby.

Rendering may use horizontal/vertical split screen, shared arena presentation or multiple board panels. Resolution/frame-rate targets are selected only after real Xbox 360 profiling; M45 does not assume 1080p split-screen is free.

### Co-op — Shared Board

Players collaborate on one board and one encounter.

Possible input models:

- alternating turns;
- simultaneous cursors;
- one player begins a word and another continues it;
- role-based actions, such as offense/support;
- shared HP/resources;
- synchronized combo attacks.

Conflicting simultaneous selections must have a deterministic resolution rule.

### Co-op — Parallel Boards

Each player has a private board but the team attacks the same enemies/boss.

This is especially suitable for network play because board interaction remains local while combat state is shared.

### Team Battle

Support 2v2 or other small-team configurations where practical:

```text
P1 + P2  vs  P3 + P4
```

The player/session abstraction should not hard-code exactly two players even if the first implementation is 1v1/2-player co-op.

## 2. Network multiplayer

### Transport priorities

M45 should separate gameplay/session logic from the transport itself.

Priority order:

1. local multiplayer;
2. LAN/System Link-style transport on Xbox 360 where the available homebrew/toolchain APIs permit it;
3. Aurora LiNK compatibility research for System Link-capable builds;
4. portable direct-IP/relay transport on supported host platforms if useful;
5. **Xbox Live / Xbox Network research backend** for native-style session/discovery features where legitimately and technically available;
6. optional community infrastructure only through documented, replaceable adapters.

Xbox Live/Xbox Network support is deliberately a **Tier 3 research/stretch transport**, not a requirement for the project. M45 must remain fully useful through local/System Link/community transports if official services cannot be used by the homebrew build.

The Xbox Live research tier may investigate:

- create/host session;
- find/discover session;
- join/leave session;
- player/session metadata;
- matchmaking/discovery abstractions;
- invites and presence where exposed;
- peer connectivity/session handoff to the same LexNet gameplay protocol.

If a required facility is unavailable, restricted or incompatible with the validated homebrew/toolchain environment, the correct outcome is a documented limitation or disabled backend — not an enforcement bypass. Services whose purpose is account/console enforcement bypass or "anti-ban" behavior are not a LexEngine dependency. M45 concerns game networking, sessions and synchronization, not defeating platform protections.

### Transport-independent session API

Gameplay code should not branch on a particular service such as LiNK or Xbox Live. It should consume a capability-driven session API, conceptually:

```cpp
LexSession_Create(...);
LexSession_Find(...);
LexSession_Join(...);
LexSession_Leave(...);
LexSession_SendInput(...);
```

Possible backends:

```text
LexSession
   |
   +-- LocalSessionBackend
   +-- SystemLinkBackend
   +-- RelayBackend
   +-- XboxLiveResearchBackend
```

`XboxLiveResearchBackend` is optional and capability-gated. The core simulation and multiplayer modes must not contain service-specific code.

### Session model

A `MultiplayerSession` should own:

- session ID;
- peers/players;
- player slots and teams;
- game-mode/ruleset ID;
- deterministic match seed;
- ready/start state;
- input sequence numbers;
- latency/jitter statistics;
- disconnect/reconnect policy;
- match result.

### Synchronization model

Begin with the simplest deterministic solution that works for the selected mode:

- synchronized lockstep where appropriate;
- delayed-input simulation where latency tolerance is acceptable;
- rollback only when justified by responsiveness requirements and proven determinism.

M21 replay/rewind snapshots are useful primitives, but they are **not automatically rollback netcode**.

Rollback requires at minimum:

- fixed deterministic simulation ticks;
- compact deterministic player inputs;
- prediction rules;
- input history;
- bounded state snapshots;
- rollback + resimulation;
- state checksums/desync detection;
- suppression/reconciliation of duplicated presentation side effects;
- rollback-window and memory budgets;
- latency/jitter testing.

For a word/puzzle RPG, lockstep or modest input delay may be preferable to aggressive rollback for many modes. M45 must measure rather than assume.

## 3. Competitive modes

### Word Duel

Classic 1v1 vocabulary combat.

A successful word may:

- deal direct damage;
- add score;
- build meter;
- apply ruleset-defined status effects;
- temporarily influence the opponent board where that ruleset explicitly allows it.

Classic single-player balance remains untouched.

### LexMath Duel

M42's arithmetic challenge providers become a competitive mode.

Example:

```text
TARGET = 42

P1: 7 × 6
P2: 50 - 8
```

Both are valid; the selected ruleset determines whether speed, complexity, efficiency or score decides the exchange.

### Time Attack / Score Race

All players solve independent boards under the same deterministic seed/ruleset and compare score/progression at defined synchronization points.

This is a low-bandwidth mode and a useful early network target.

---

## 4. Cooperative modes

### Boss Raid

Two to four players attack one shared boss.

Each player may have an independent board while the boss owns authoritative shared combat state:

- HP;
- phase;
- status effects;
- team meter;
- encounter timer;
- scripted transitions.

A fire/status word from one player can therefore influence the same boss state observed by every peer.

### Shared-Word Combo

A cooperative ruleset allows players to contribute sequential segments to one challenge/word.

Example:

```text
P1: PRO
P2: GRAM
    -----
    PROGRAM
```

The exact legality rules must be deterministic and defined by the mode rather than embedded in generic input code.

### Team Support

Players may specialize through explicit ruleset roles such as:

- attacker;
- healer/support;
- board cleaner;
- status control.

Roles are game-mode data, not platform concepts.

---

## 5. Party modes

### Hot Potato

Two to four players share a board and a countdown object.

- complete a valid challenge before the timer expires;
- success passes control to the next player;
- timer pressure increases as the round continues;
- the player holding the "bomb" at expiry loses the round or takes the configured penalty.

The same mode can use words or LexMath challenges through the challenge-provider API.

### Relay

Players alternate contributions toward a shared sequence of challenges. Streaks reward clean hand-offs and team consistency.

### Draft Board

Players take turns claiming useful tiles/resources from a common pool before a short duel or score round.

### Survival Rotation

Players rotate into a continuing encounter; each player must survive or improve the team's state before handing control onward.

---

## 6. Asymmetric / Kinect modes

### Kinect Commander

An optional local asymmetric mode:

- controller player uses the normal board/combat interface;
- Kinect player acts as a commander/opponent through supported gestures;
- commander actions manipulate explicitly defined encounter mechanics rather than arbitrary engine state.

Examples may include spawning hazards, selecting curses or triggering board modifiers.

This mode depends on successful M40 Kinect research and must always have a non-Kinect fallback if it becomes shipping content.

### Mixed-device local play

Where supported, different players may use different LexInput devices while the game mode consumes normalized actions rather than device-specific APIs.

---

## 7. Single-player counterparts

M45's rule modules should not become useless when no second player is present. Selected modes get solo variants that reuse the same systems.

### Boss Raid Solo

Endurance battle against the raid boss using the same phase/status rules as multiplayer, scaled for one player.

### Time Bomb

Solo Hot Potato variant:

- countdown continuously decreases;
- valid challenges add time or damage;
- harder/longer solutions may grant larger bonuses;
- run ends on timer expiry or encounter completion.

### Puzzle / LexMath Academy

Untimed and timed solo challenge sets using M42's arithmetic providers, progression and mastery tracking.

### Kinect Trial

If M40 succeeds, a solo challenge mode can combine normalized gesture input with board/combat challenges without making Kinect mandatory for the core game.

### Ghost Challenge

Record a deterministic input/score trace from a completed run and race against that trace later without requiring a live remote peer.

Names are provisional; architecture is more important than filenames.

```text

├── multiplayer/
│   ├── multiplayer_session.*
│   ├── player_slot.*
│   ├── game_mode_director.*
│   ├── input_history.*
│   ├── state_checksum.*

│   └── packet_codec.*

    └── xbox360/
        └── network_xbox360.*
```

Presentation-specific split-screen routing belongs with presentation/render code rather than deterministic game state.

## 9. Desync and validation tooling

Network correctness is a first-class requirement.

Provide:

- deterministic seed logging;
- per-tick or periodic state hashes;
- input-stream recording;
- desync dump containing recent inputs + checksums;
- replay of a captured network match on host builds;
- artificial latency/jitter/loss simulation;
- disconnect/reconnect test cases;
- long soak tests.

No competitive ruleset should depend on nondeterministic local wall-clock timing for gameplay outcomes.

---

## 10. Relationship to LexMod

The multiplayer layer should allow LexMod packages to define game-mode rules through documented APIs while transport/session integrity remains engine-owned.

Examples:

```text
Classic Word Duel     -> Word challenge provider
LexMath Duel          -> Arithmetic challenge provider
Hot Potato            -> generic timed challenge wrapper
Boss Raid             -> cooperative encounter rules
```

Mods must not be given arbitrary raw network packet hooks by default. Prefer validated, versioned game-mode messages/events.

---

## Definition of Done

M45 is complete when the project demonstrates, with documented builds/tests:

- [ ] reusable player/session abstraction;
- [ ] at least two local players with independent normalized input;
- [ ] local Versus mode;
- [ ] local Co-op mode;
- [ ] one party mode (Hot Potato recommended);
- [ ] one solo counterpart using the same rules infrastructure;
- [ ] Xbox 360 LAN/System Link-style session if the validated homebrew APIs permit it;
- [ ] Aurora LiNK compatibility investigated/documented for the System Link path;
- [ ] Xbox Live/Xbox Network session APIs researched and documented for the validated environment; if legitimately/technically usable, a minimal create/find/join proof of concept is demonstrated, otherwise the blocker is recorded;
- [ ] at least one networked Versus or Co-op match on a supported transport;
- [ ] deterministic state checksum/desync diagnostics;
- [ ] latency/jitter/loss test harness;
- [ ] rollback implemented only if measurements justify it, with deterministic resimulation tests;
- [ ] LexMath Duel or LexMath Co-op demonstration;
- [ ] documentation for adding multiplayer-capable LexMod game modes;
- [ ] real Xbox 360 validation for local multiplayer and any Xbox-specific networking path that ships.

M45 must not require official Xbox network services, platform-enforcement bypasses or proprietary server infrastructure to preserve basic multiplayer functionality. Xbox Live/Xbox Network is a supported **research target**, not a guaranteed shipping transport.
